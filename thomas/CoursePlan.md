# Course plan
| # | Lecture and learning goal | Workshop and evidence | Free hands-on practice | Free resources |
|---|---|---|---|---|
| **1** | **Security foundations and threat modelling.** Introduce confidentiality, integrity, availability, assets, threats, vulnerabilities, and risk. Explain what a trust boundary tells a developer. | Map the browser, API, database, and deployment environment. Identify three plausible threats and rank them by likelihood and impact. **Hand in:** a one-page data-flow diagram and prioritized risk list. | [OWASP Threat Dragon](https://owasp.org/www-project-threat-dragon/) — create a simple data-flow diagram and threat model. | [OWASP Threat Modeling](https://community.owasp.org/Threat_Modeling) · [OWASP Top 10](https://owasp.org/projects/Top-Ten). ([community.owasp.org][1]) |
| **2** | **Linux and deployment boundaries.** Cover processes, service accounts, file permissions, listening ports, and least privilege. | Use a local container or instructor-provided terminal output to inventory services and permissions. Compare the current setup with a design where only the reverse proxy is publicly reachable. **Hand in:** a service inventory and one verified hardening change. | TryHackMe [Linux Fundamentals Part 1](https://tryhackme.com/room/linuxfundamentalspart1), selected tasks. ([tryhackme.com][2]) | — |
| **3** | **DNS, HTTPS, and HTTP.** Trace a request from hostname resolution through TLS termination at the reverse proxy to the Java API. | Inspect a normal request in browser DevTools and a supplied local HTTPS trace. Identify where TLS terminates, where headers are added, and which services need network access. **Hand in:** an annotated request trace and one check for HTTPS or a security header. | TryHackMe [DNS in Detail](https://tryhackme.com/room/dnsindetail) and [Web Application Basics](https://tryhackme.com/room/webapplicationbasics), selected DNS and header tasks. ([tryhackme.com][2]) | — |
| **4** | **Authentication, password storage, and sessions.** Distinguish hashing, encryption, and signing. Compare cookie-backed sessions and JWTs, then use the starter app’s approach for implementation. | Review what happens at login, expiry, and logout. Check password hashing through a vetted library and verify the chosen session or token expiry behavior. **Hand in:** a short lifecycle diagram and tests for a valid login, a rejected login, and expiry. | [PortSwigger Web Security Academy: Authentication](https://portswigger.net/web-security/authentication) — selected practice labs. | OWASP [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). ([OWASP Cheat Sheet Series][3]) |
| **5** | **Authorization and object ownership.** Distinguish roles from ownership, and show where Javalin should enforce each rule. | Write a permissions matrix for anonymous users, ticket owners, other signed-in users, and support staff. Implement the server-side policy and cover the matrix with Rest-Assured tests. **Hand in:** the matrix and test results for allowed and denied actions. | [PortSwigger Web Security Academy: Access control](https://portswigger.net/web-security/access-control) — selected practice labs. | OWASP [Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) and [ASVS](https://asvs.owasp.org/). ([OWASP Cheat Sheet Series][4]) |
| **6** | **Untrusted input, database queries, and safe errors.** Explain what DTO validation, parameterized queries, and consistent error responses each protect. | Review a ticket-search feature. Add validation at the API boundary, bind query parameters in JPA or JDBC, and return useful errors without exposing internals. **Hand in:** tests covering valid input, malformed input, and ordinary text containing punctuation. | [PortSwigger Web Security Academy: SQL injection](https://portswigger.net/web-security/sql-injection) — selected practice labs. | OWASP [SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html) and the [Cheat Sheet Series](https://cheatsheetseries.owasp.org/). ([OWASP Cheat Sheet Series][5]) |
| **7** | **Browser security.** Explain the same-origin policy, CORS, XSS prevention, and CSRF in the context of a React frontend. | Render ticket comments as text, inspect the app’s origin policy, and verify the intended browser behavior. If the app uses cookie-based authentication, also verify the protection on a state-changing request. **Hand in:** a browser verification checklist with expected and observed results. | PortSwigger Web Security Academy [XSS](https://portswigger.net/web-security/cross-site-scripting), [CSRF](https://portswigger.net/web-security/csrf), and [CORS](https://portswigger.net/web-security/cors) practice labs. | [MDN CORS guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) · OWASP [XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) and [CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). ([MDN][6]) |
| **8** | **Dependencies and CI/CD.** Cover direct and transitive dependencies, advisory triage, build secrets, and workflow permissions. | Review findings from the Maven and npm parts of the project. Choose one finding, explain its relevance to the app, and verify an upgrade by running tests. Review one GitHub Actions job or Docker build for unnecessary permissions or secret exposure. **Hand in:** a dependency decision and a configuration diff. | [GitHub Skills](https://skills.github.com/) — free interactive exercises for GitHub workflows and Actions. | [OSV-Scanner](https://google.github.io/osv-scanner/) · [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use) · [Docker build secrets](https://docs.docker.com/build/building/secrets/). ([google.github.io][7]) |
| **9** | **Security logging and detection.** Explain which events to record, which sensitive data to omit, and how to correlate application and proxy events. | Add structured events for failed login and denied access, with a request ID. Give students synthetic logs containing normal traffic and suspicious activity. **Hand in:** a correlated timeline and one alert idea, including a plausible false positive. | Optional TryHackMe [Linux Process Analysis](https://tryhackme.com/room/linuxprocessanalysis) for students ready to examine host evidence. | [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) |
| **10** | **Phishing triage and incident response.** Distinguish an observation from a conclusion and decide what evidence would change the response. | Inspect the headers and visible indicators in a supplied training email. Run a tabletop exercise where a support employee reports possible credential disclosure and the instructor releases new evidence in stages. **Hand in:** a timeline and the first three response actions, each with a reason. | TryHackMe [ParrotPost: Phishing Analysis](https://tryhackme.com/room/parrotpost), header-analysis portion. ([TryHackMe][9]) | [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final), selected sections. |
| **11** | **Security verification and peer review.** Turn requirements into checks and distinguish verified, partially verified, and unverified controls. | Pairs exchange projects and review three selected ASVS requirements using code, configuration, and test evidence. Each pair challenges one assumption in the other pair’s threat model. **Hand in:** a review with evidence, severity, and a proposed fix or follow-up check. | [OWASP Juice Shop](https://owasp.org/www-project-juice-shop/) — use a local or instructor-provided instance for controlled practice. | [OWASP ASVS 5.0](https://asvs.owasp.org/) · [OWASP Threat Modeling](https://community.owasp.org/Threat_Modeling). ([OWASP Application Security Verification Standard][10]) |
| **12** | **Capstone demonstration and handover.** Defend the most important security decisions and explain what risk remains. | Students demonstrate two controls with verification evidence, explain one finding from peer review, and respond to one new incident clue. **Hand in:** the final repository, revised threat model, and a short security report. | Continue with the course project in its approved environment, or use a local [OWASP Juice Shop](https://owasp.org/www-project-juice-shop/) instance for extra practice. | Reuse the selected [ASVS requirements](https://asvs.owasp.org/) and [NIST incident response guidance](https://csrc.nist.gov/pubs/sp/800/61/r3/final). ([OWASP Application Security Verification Standard][10]) |
